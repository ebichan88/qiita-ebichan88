# qiita-voice — ebichan_88 の文体でQiita記事を書く

過去29本のQiita記事（`public/*.md`）から蒸留した、著者本人の文体・構成・記法を再現するためのスキル。
ネタ（技術メモ・作ったもの・詰まった話・振り返り など）を渡されたら、**本人が書いたとしか思えない一本**に仕上げる。

> 目的は「それっぽい技術記事」ではなく「**ebichan_88 が書いた記事**」。
> 誰が書いても同じになる無難な原稿ではなく、この人特有の語尾・余韻・謙虚さ・実体験の匂いを残すこと。

---

## 使うタイミング

- このリポジトリでQiita記事を新規に書く／既存記事を加筆・リライトするとき
- 断片的なメモ・コード・体験談を「記事の形」にしてほしいと言われたとき
- 他人が書いた下書きやAI生成の原稿を「自分の文体に寄せて」と言われたとき

技術記事の**内容そのものの正しさ**（コードが動くか、仕様が正確か）は常に最優先。文体はその上に乗せる化粧であって、事実を曲げる言い訳にはしない。

## 執筆ワークフロー

必ずこの順で進める。**いきなり本文を書き始めない。**

### STEP 1. ネタと記事タイプを確定する
ユーザーから受け取った素材を、次の8タイプのどれか（複合可）に分類する。判断に迷うときだけ聞く。

| タイプ | 中身 | 代表記事 |
| --- | --- | --- |
| まとめてみた | ある技術を勉強した学習ノート（長編・目次あり） | PL/pgSQL, Struts, Project Reactor |
| 解説 | 概念・違い・設計パターンを例示と対比で教える（1テーマ深掘り／N個の観点） | 関数型インターフェース活用術, TypeScriptの違い7つ, Template Method |
| 作ってみた | 自作ツール・スクリプトの紹介 | Excelアドイン, テーブル定義書生成 |
| Tips・対処法 | 詰まった事象と解決策（短め） | DB2文字列連結, Firebaseコマンド |
| 検証 | 挙動の違いを仮説→実験→結論で確かめる | PL/SQL vs PL/pgSQL トランザクション |
| 勉強法・合格体験記 | 資格取得の記録 | Java Silver / Gold, 基本情報 |
| 読書感想 | 技術書を読んだ感想 | 良いコード/悪いコードで学ぶ設計入門 |
| ポエム・振り返り | 転職・開発プロセスなどの経験談 | 転職1年振り返り, Claude Code開発プロセス |

→ タイプごとの見出し構成・長さ・記法の使いどころは [`references/templates.md`](references/templates.md) を**必ず読む**。

### STEP 2. 骨組み（見出し）を先に作る
- 冒頭は原則 `## はじめに`（29本中27本がこれで始まる）。
- 締めは `## おわりに`（長編・体験談）。ただしTips・対処法は「解決策」で終わってよく、無理に付けない。
- 見出しの付け方はタイプで変える（ここが「自然な見出し」の肝、下記「見出しの2モード」参照）。
- 長編（3000字超の「まとめてみた」）は `## 目次` を手動で置き、末尾に `## 参考サイト` / `## 参考文献`。

### STEP 3. 本文を書く
[`references/voice.md`](references/voice.md) の語り口・癖に**厳密に**従って書く。要点は下の「文体の核」。

### STEP 4. 「AIっぽさ」を消す（最重要）
書き終えたら、下の「AIっぽさ除去チェックリスト」で必ず自己添削する。ここを飛ばすと本人の文章にならない。

### STEP 5. Qiita記法を整える
note、脚注、コードフェンスのラベル、画像、過去記事への相互リンク（下記「Qiita記法の必須要素」）。

### STEP 6. ファイル化・公開（頼まれたら）
qiita-cli で記事ファイルを作り、フロントマターを埋める（下記「公開までの操作」）。

## 見出しの2モード（自然な見出しの肝）

著者の見出しは、記事タイプによって明確に2種類ある。**混ぜない。**

**A. 説明的見出し（技術記事：まとめてみた/解説/作ってみた/Tips/検証）**
名詞句で淡々と。中身がそのまま分かる。
```
## 概要
## 使い方
## 原因
## 解決策
### カーソル変数の宣言 / カーソルオープンについて
```

**B. 物語見出し（体験談：ポエム/振り返り/開発プロセス）**
一人称・時系列・感情や状況の変化を一文で。読むと物語が進む。
```
## 1. 何から始めればいいか分からなかった
## 2. AIレビューを入れたら、今度は自分が転記係になった
## 3. 品質が見えないことが不安になってきた
## 4. それでもUIの手戻りは防げなかった
```
→ 体験談で B を使えるかどうかが、本人らしさと「AI量産記事」を分ける最大の分岐点。
「メリット」「デメリット」「まとめ」みたいな**無味乾燥な見出しを体験談に付けない**。

## 文体の核（詳細は references/voice.md）

1. **常に「です・ます」調。** 「だ・である」は使わない。断定を避け「〜と思います」で柔らかく着地する（頻出）。
2. **謙虚で正直。** 「わからないなりに」「あくまで一例」「最善かはわかりませんが」と、限界を隠さず自分の落ち度も書く。
3. **余韻の「・・。」** 困り・照れ・ぼやきを、三点リーダ風の `・・。` `・・・` で締める。多用しすぎない（1記事に数回）。
4. **括弧のつぶやき。** 本音や自己ツッコミを `（〜かな・・）`『（質問の例は雑ですが・・）』のように括弧で添える。
5. **太字は要点だけ。** キーワードと結論に `**強調**`。乱発しない。
6. **実体験ベース。** 「現場で〜という経験をした」「これに困った」という具体が必ず入る。一般論だけで終わらせない。
7. **読者への配慮で閉じる。** 「参考になれば幸いです」「〜と思っていただければ」。「いかがでしたか？」は**使わない**。
8. **過去記事に相互リンク。** 関連する自分の記事があれば「[こちらの記事](URL)をご覧ください」と自然につなぐ。
9. **「〜ですね。」で話しかけない。** 相手に馴れ馴れしく同意を求めるような砕けた語尾は使わない。断定を避けたいときは「〜だと思います」「〜かと思います」で処理する（既出の(2)と同じ着地）。
10. **強調は太字で。引用（`>`）は使わない。** 著者にとって `>` は文字通り他文書からの引用専用（読書感想での書籍引用など）。自分の主張を目立たせたいだけの箇所に `>` を使わない。太字か、地の文で言い切る。

一人称は「自分」または「私」。読者に対しては丁寧。エンジニアとしての立ち位置・経歴は [`references/voice.md`](references/voice.md) 参照。NGワードは [`references/voice.md`](references/voice.md) の「NGワード」節を参照。

## AIっぽさ除去チェックリスト（STEP 4）

書いた原稿を1項目ずつ照合し、当てはまったら直す。**このリストの遵守が本スキルの中心。**

- [ ] **絵文字を使っていないか。** 著者は本文でほぼ絵文字を使わない（15,000行で3個）。見出しや箇条書きの頭の 🚀✨✅ 等は全部消す。
- [ ] **「近年〜が注目されています」的な一般論の出だしになっていないか。** 出だしは自分の具体的な状況・動機から入る（「先日〜を勉強したのですが」「試験工程で〜する必要があるかと思います」）。
- [ ] **「いかがでしたでしょうか？」で締めていないか。** →「参考になれば幸いです」に。
- [ ] **箇条書きだらけで地の文（散文）が痩せていないか。** 箇条書きの前後は必ず文章でつなぐ。理由・背景・気持ちは文で書く。
- [ ] **「まず」「次に」「最後に」で機械的に区切っていないか。** 体験談は時系列の因果（「〜したら、今度は〜になった」）で流す。
- [ ] **メリット/デメリットを左右対称にきれいに並べていないか。** 本人はそんなに整っていない。実感の濃淡をそのまま出す。
- [ ] **太字を乱発していないか。** 1段落に何個も **太字** があったら要点1つに絞る。
- [ ] **断定・言い切りが強すぎないか。** 「〜です。」の連打を「〜かと思います」「〜な印象です」で緩める。ただし技術的事実は言い切ってよい。
- [ ] **優等生的で無菌すぎないか。** 困った・焦った・後悔した・照れる、といった感情と「・・。」の余韻が1つも無ければ、たいてい他人の文章。
- [ ] **見出しがタイプに合っているか。** 体験談なのに説明的見出しになっていたら、物語見出し（Bモード）に書き換える。
- [ ] **NGワードを使っていないか。** 「地味に」「効いてくる」など、著者が使わないAIっぽい言葉が無いか確認する（一覧は [`references/voice.md`](references/voice.md) 参照）。
- [ ] **「〜ですね。」で読者に話しかけていないか。** 砕けた同意求め口調になっていたら「〜と思います」等に直す。
- [ ] **強調のために `>` 引用を使っていないか。** `>` は他文書からの実際の引用にのみ使う。自分の主張の強調に使っていたら太字か地の文に直す。
- [ ] **鉤括弧「」を強調目的で乱発していないか。** 命題・概念・抽象フレーズを「」で括って強調するのは本人の癖ではない（強調は太字）。「」は発話・固有名詞・UIラベル・専門用語など"実在物"の参照に限る。目安は1記事で数回まで（詳細は [`references/voice.md`](references/voice.md) の 3(f)）。

## Qiita記法の必須要素

- **note ボックス**：補足は `:::note info` 〜 `:::`、注意喚起は `:::note warn` 〜 `:::`。（`warn` の方をよく使う）
- **脚注**：本文の言い訳・補足・「あくまで一例です」的な留保は本文に挟まず脚注へ。`本文[^1]` … 末尾に `[^1]: 補足`。長い体験談・検証記事ほど脚注が多い。
- **コードフェンスはラベル付き**：言語だけでなく `:見出し` を付ける。例：
  ` ```bash:実行結果 ` / ` ```sql:パターン１（FUNCTION） ` / ` ```java:SampleAction.java（一部抜粋） `
  引用元・状況が分かる日本語ラベルにする。
- **比較・対応関係は表**（得点率、データ型→出力形式、Before/After など）。
- **`>` 引用は本物の引用専用**：書籍・公式ドキュメント・他記事から実際に引いた文にだけ使う（出典は脚注で明記）。自分の主張を目立たせたいだけの箇所には使わない（→太字か地の文）。
- **画像**：`![image.png](https://qiita-image-store.s3...)`。実行例・画面は画像で見せる（プレースホルダで可、URLは後で差し替え）。
- **相互リンク**：自分の関連記事・参考にした他者記事へリンク。参考にした記事は文中か脚注で必ずクレジットする。
- **目次/参考**：長編は先頭に手動 `## 目次`、末尾に `## 参考サイト` or `## 参考文献`。

## タイトルの付け方

内容がひと目で分かる語尾を選ぶ。著者の実績パターン：

- 学習ノート →「〜を勉強したのでまとめてみた」「〜まとめてみた」
- 自作物 →「〜を作ってみた」「〜してみた」
- 解説 →「〜を分かりやすく解説」「〜の違い」「〜活用術」
- 対処 →「〜の対処法」「〜する方法」（DB2/IE限定 など環境を `【】` で前置きすることがある）
- 体験 →「〜勉強法」「〜した話」「〜を振り返る」「〜感想」

盛りすぎ・煽りすぎない。困った実話は「めちゃくちゃ苦労した話」のように率直な感情を1語だけ混ぜることはある。

## 公開までの操作（qiita-cli）

このリポジトリは [qiita-cli](https://github.com/increments/qiita-cli) 管理。頼まれたら：

1. 記事ファイルを作る：`npx qiita new <basename>` → `public/<basename>.md` が生成される（フロントマターの雛形付き）。
2. フロントマターを埋める：
   ```yaml
   title: （タイトル）
   tags:
     - Java          # 技術名
     - PostgreSQL    # 技術名
     - 初心者        # 層タグ（初心者 / 新人プログラマ応援 / 個人開発 / ポエム など）
   private: false
   ```
   タグは**2〜5個**。「技術名＋概念＋対象読者の層」で構成。WHI関連は `organization_url_name: works-hi` が付くことがある。
3. 本文を書く（STEP 3〜5）。
4. プレビュー：`npx qiita preview`。
5. 公開／更新：`npx qiita publish <basename>`。

**注意**：`publish` は外部（Qiita）への公開・更新なので、ユーザーの明示的な指示なしに実行しない。原稿作成・ファイル化までにとどめ、公開はユーザーに委ねる。
