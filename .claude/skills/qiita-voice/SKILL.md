# qiita-voice — ebichan_88 の文体でQiita記事を書く

過去のQiita記事（`public/*.md`）から蒸留した、著者本人の文体・構成・記法を再現するためのスキル。
ネタ（技術メモ・作ったもの・詰まった話・振り返り など）を渡されたら、**本人が書いたとしか思えず、知らない人が読んでも面白く役に立つ一本**に仕上げる。

目的は3つあり、どれか1つでも欠けると記事として失敗する。

1. **本人の言葉で書く。** 動機・苦労・感想・こだわりは、本人から聞いた内容だけで書く。リポジトリや素材から推測した感情・経験・意見を足さない（足すと「文体は似ているが空虚な記事」になる）。
2. **読者にとって面白く、役に立つ。** 文体を忠実に再現しても、知らない人が読んで面白くなければ失敗。特にツール紹介は「何ができるか」が具体的に伝わることが最優先。
3. **本人の文体で書く。** 基準は最近の記事（Project Reactor・Template Method等）の書き言葉寄りの文体。古い記事の口語的な癖を真似ない。

技術記事の**内容そのものの正しさ**（コードが動くか、仕様が正確か、数式が実装と合っているか）は常に最優先。文体はその上に乗せる化粧であって、事実を曲げる言い訳にはしない。

---

## 使うタイミング

- このリポジトリでQiita記事を新規に書く／既存記事を加筆・リライトするとき
- 断片的なメモ・コード・体験談を「記事の形」にしてほしいと言われたとき
- 他人が書いた下書きやAI生成の原稿を「自分の文体に寄せて」と言われたとき

## 執筆ワークフロー

必ずこの順で進める。**いきなり本文を書き始めない。**

### STEP 1. ネタと記事タイプを確定する
ユーザーから受け取った素材を、次の8タイプのどれか（複合可）に分類する。判断に迷うときだけ聞く。

| タイプ | 中身 | 代表記事 |
| --- | --- | --- |
| まとめてみた | ある技術を勉強した学習ノート（長編・目次あり） | PL/pgSQL, Struts, Project Reactor |
| 解説 | 概念・違い・設計パターンを例示と対比で教える（1テーマ深掘り／N個の観点） | 関数型インターフェース活用術, TypeScriptの違い7つ, Template Method |
| 作ってみた | 自作ツール・スクリプトの紹介 | dbxray, Excelアドイン, テーブル定義書生成 |
| Tips・対処法 | 詰まった事象と解決策（短め） | DB2文字列連結, Firebaseコマンド |
| 検証 | 挙動の違いを仮説→実験→結論で確かめる | PL/SQL vs PL/pgSQL トランザクション |
| 勉強法・合格体験記 | 資格取得の記録 | Java Silver / Gold, 基本情報 |
| 読書感想 | 技術書を読んだ感想 | 良いコード/悪いコードで学ぶ設計入門 |
| ポエム・振り返り | 転職・開発プロセスなどの経験談 | 転職1年振り返り, Claude Code開発プロセス |

→ タイプごとの見出し構成・長さ・記法の使いどころは [`references/templates.md`](references/templates.md) を**必ず読む**。

素材がリポジトリ（自作ツール等）の場合は、READMEだけでなくコミット履歴・Issue・設計文書・コードまで読み、事実を集める。サンプルデータがあれば実際に動かして出力を取る（記事の実行例は本物を使う）。

### STEP 2. 骨組み（見出し）を先に作る
- 冒頭は原則 `## はじめに`。締めは `## おわりに`（長編・体験談）。Tips・対処法は「解決策」で終わってよい。
- 見出しの付け方はタイプで変える（下記「見出しの2モード」）。
- 長編（3000字超）は `## 目次` を手動で置く。`## 参考サイト` / `## 参考文献` は、**本文でまだリンクしていない資料がある場合だけ**置く（必須ではない）。
- 骨組みは「読者が知りたい順」に並べる。ツール紹介なら、何ができるか → 実際の出力 → 読者が抱く疑問への答え → 仕組み、の順（templates.md の「作ってみた」）。

### STEP 3. ヒアリングする（本人の言葉を集める）
骨組みができたら、本文を書く前に**本人にしか書けない項目を洗い出して質問する**。詳細は下記「ヒアリング」節。
構成案とヒアリングの質問はまとめて1回で提示し、回答を待ってから書く。

### STEP 4. 本文を書く
[`references/voice.md`](references/voice.md) の語り口に従って書く。要点は下の「文体の核」。
本人の回答は、意味を変えずに書き言葉へ整えて使う。回答に無い感情・経験・意見・今後の予定は書かない。

### STEP 5. 読者視点で見直す
書き終えたら、下の「読者視点チェックリスト」で見直す。**文体のチェックより先に行う**（構成や章の取捨選択が変わるため）。

### STEP 6. 「AIっぽさ」を消す
下の「AIっぽさ除去チェックリスト」で自己添削する。

### STEP 7. Qiita記法を整える
note、脚注、コードフェンスのラベル、コード表記、画像（下記「Qiita記法の必須要素」）。
ツールの出力などの画面キャプチャが要る場合は [`references/captures.md`](references/captures.md) の手順で撮る。

### STEP 8. ファイル化・公開（頼まれたら）
qiita-cli で記事ファイルを作り、フロントマターを埋める（下記「公開までの操作」）。

## ヒアリング（STEP 3）

本人の言葉が無い記事は、文体が似ていても空虚になる。次の項目は**推測で書かず、必ず本人に聞く**。

| 聞く項目 | 例 |
| --- | --- |
| 動機・きっかけ | なぜ作った／勉強したか。業務の具体的な場面 |
| 経緯の中の判断 | 機能を足した理由、方針を決めた理由。自分の判断かAIの提案か |
| 苦労・うれしかったこと | 具体的な出来事と、そのときの気持ち |
| 使ってみた実感 | 便利だった場面、物足りない点 |
| 記事で扱いたい範囲 | 厚く書きたい章、触れたくない話題、書いてほしくないこと |
| 読者に伝えたいこと | 誰に使ってほしいか、締めの一言 |
| 名前・タイトル・公開設定 | 名前の由来、タイトルの好み、タグ、Organization（works-hi）に紐づけるか |

- 質問は番号付きで、必須と任意を分ける。答えやすいよう、リポジトリから分かった事実（時系列・規模など）を先に示し、間違いがあれば直してもらう。
- 回答が無い項目は、記事から外すか、リポジトリから分かる事実だけにとどめる。
- AIに作ってもらった部分が多い場合は、本人が「自分の言葉で語れる」範囲を確認し、語れない設計判断を本人のこだわりのように書かない。
- 本人の言い回しを書き換えると意味やニュアンスが変わりそうな箇所（感情の表現、本人が使った比喩など）は、言い換え案を出して本人に選んでもらう。

## 見出しの2モード（自然な見出しの肝）

著者の見出しは、記事タイプによって明確に2種類ある。**混ぜない。**

**A. 説明的見出し（技術記事：まとめてみた/解説/作ってみた/Tips/検証）**
名詞句で淡々と。中身がそのまま分かる。
```
## 概要
## 使い方
## 出力されるドキュメント
## 整備されていないDBで使うための機能
### 業務の言葉でテーブルを探す
```

**B. 物語見出し（体験談：ポエム/振り返り/開発プロセス）**
一人称・時系列・感情や状況の変化を一文で。読むと物語が進む。
```
## 1. 何から始めればいいか分からなかった
## 2. AIレビューを入れたら、今度は自分が転記係になった
## 3. 品質が見えないことが不安になってきた
```
→ 体験談で B を使えるかどうかが、本人らしさと「AI量産記事」を分ける分岐点。
「メリット」「デメリット」「まとめ」みたいな**無味乾燥な見出しを体験談に付けない**。

## 文体の核（詳細は references/voice.md）

1. **常に「です・ます」調。** 「だ・である」は使わない。意見は「〜と思います」「〜と感じました」で着地し、技術的事実は言い切る。
2. **書き言葉を基準にする。** 最近の記事の文体に合わせる。「以下の」より「次の」、「〜なので」より「〜のため」、「手を入れる」「出せる」「引ける」のような話し言葉は書き言葉に直す（言い換えの例は voice.md の「書き言葉への言い換え」）。
3. **冗長にしない。** 「〜ようなこと」「〜するようにしていて」「〜しようと思っていた…しようと思った」のような重なりを削る。1文1行、段落は1〜2文。
4. **誠実だが、記事の価値を下げない。** 扱う範囲を区切る・限界を脚注で添えるのはよい。一方で「まだ実務で使っていない」のような、紹介する意味自体を損なう但し書きは書かない。
5. **括弧で補足しない。** 文章として書けるものは文章で書く。括弧のつぶやき・自己ツッコミは原則使わない（用語の言い換え・コードの書式など、括弧でしか書けないものは残してよい）。
6. **「・・。」は本人の感情の箇所だけ。** 本人の回答にある感情を表す箇所に限り、1記事に0〜1回。演出のために足さない。
7. **太字は要点だけ。** キーワードと結論に `**強調**`。乱発しない。
8. **実体験は本人の言葉で。** 一般論だけで終わらせないが、実体験は STEP 3 で聞いた内容だけを書く。
9. **読者への配慮で閉じる。** 「参考になれば幸いです」「ぜひお勧めします」等。「いかがでしたか？」は**使わない**。
10. **「〜ですね。」で話しかけない。** 断定を避けたいときは「〜だと思います」で処理する。
11. **強調は太字で。引用（`>`）は使わない。** `>` は他文書からの実際の引用専用。

一人称は「自分」または「私」。読者に対しては丁寧。エンジニアとしての立ち位置・経歴は [`references/voice.md`](references/voice.md) 参照。

## 読者視点チェックリスト（STEP 5）

その記事を全く知らない人が読む前提で、1項目ずつ確かめる。当てはまったら構成・章ごと直す。

- [ ] **冒頭の1文で、何の記事か分かるか。** 作ってみた・解説は「〜を作成したので紹介します」のように目的から入り、経緯は1〜2文に絞る。
- [ ] **読者が知らない前提を膨らませていないか。** 前作との比較・旧名・社内事情などは、1文か `:::note info` で済ませる。章を立てない。
- [ ] **「何ができるか」を具体例で見せているか。** 実際の出力・キャプチャ・実行結果・質問例を、仕組みの説明より先に置く。
- [ ] **読者が抱く疑問に答えているか。** 「うちの環境では使えないのでは」「すぐ古くなるのでは」といった疑問を想定し、機能をその答えとして出す。
- [ ] **仕様の細部を書いていないか。** 終了コード・既定値・オプションの細則・設定の誤りの扱いなどはREADME・リファレンスに任せ、リンクで済ませる。
- [ ] **技術的な知見は、その記事の読者に役立つか。** ツールを使わない人にも役立つもの（例：テーブル情報を取るSQL、類似度の計算方法）は残す。当たり前の話・特定の実装でしか役立たない注意点は削る。
- [ ] **記事の価値を下げる但し書きが無いか。** 「まだ使っていない」「AIが作ったのでよく分からない」等を、本人の希望なしに書いていない。
- [ ] **相互リンク先は、本当にこの記事の内容と対応しているか。** 似た話題というだけでリンクすると誤解を招く（例：別の開発プロセスの記事を「詳しくはこちら」と案内する）。
- [ ] **数式・アルゴリズムの説明は実装と一致し、前提から段階的に説明しているか。** 例：重み付きJaccard係数の前に、通常のJaccard係数を示す。サンプルデータで手計算して確かめる。
- [ ] **同じ説明が2か所に無いか。** 新しい段落を足したら、前後に同じ理由・説明が残っていないか確かめる。

## AIっぽさ除去チェックリスト（STEP 6）

書いた原稿を1項目ずつ照合し、当てはまったら直す。

- [ ] **絵文字を使っていないか。** 見出しや箇条書きの頭の 🚀✨✅ 等は全部消す。
- [ ] **「近年〜が注目されています」的な一般論の出だしになっていないか。** 出だしは記事の目的（作ってみた・解説）か、自分の具体的な状況（体験談・学習ノート）から入る。
- [ ] **「いかがでしたでしょうか？」で締めていないか。**
- [ ] **箇条書きだらけで地の文が痩せていないか。** 箇条書きの前後は文章でつなぐ。
- [ ] **「まず」「次に」「最後に」で機械的に区切っていないか。** 体験談は時系列の因果で流す。
- [ ] **メリット/デメリットを左右対称にきれいに並べていないか。**
- [ ] **太字を乱発していないか。**
- [ ] **話し言葉・冗長な言い回しが残っていないか。** voice.md の「書き言葉への言い換え」の表と照合する。
- [ ] **括弧で補足していないか。** 本文の `（〜）` を1つずつ見て、「削除」「文章として書き直す」「残す（用語の言い換え・コード等）」のどれかに分ける。
- [ ] **「・・。」を演出で足していないか。** 本人の回答にある感情の箇所以外は消す。
- [ ] **見出しがタイプに合っているか。**
- [ ] **NGワードを使っていないか。**（一覧は [`references/voice.md`](references/voice.md)）
- [ ] **「〜ですね。」で読者に話しかけていないか。**
- [ ] **強調のために `>` 引用を使っていないか。**
- [ ] **鉤括弧「」を強調目的で乱発していないか。** 「」は発話・固有名詞・UIラベル・検索語などの実在物の参照に限る。

## Qiita記法の必須要素

- **note ボックス**：補足は `:::note info` 〜 `:::`、注意喚起は `:::note warn` 〜 `:::`。前作との関係・バージョン等の前提は info、パスワードの扱いのような注意は warn にまとめる。
- **脚注**：本文の補足・留保・用語の説明は本文に挟まず脚注へ。用語（MCP等）は本文に説明を挟まず、初出に脚注を付けて定義と公式サイトを書く。
- **コード表記**：ツール名・コマンド・ファイル名・テーブル名・カラム名・設定キーは `` `dbxray` `` のようにコード表記にする。
- **コードフェンスはラベル付き**：例 ` ```bash:実行結果 ` / ` ```java:SampleAction.java（一部抜粋） ` / ` ```json:find_similar_tables（table: employee）の結果 `。載せるコードは、それを読むことで新しく分かることがあるものだけにする。
- **AIへの質問例・利用者の発話の例**：太字の箇条書きにする（例：`- **employeeと構造が似たテーブルはある？**`）。
- **比較・対応関係は表**。
- **`>` 引用は本物の引用専用**。
- **画像**：`![説明](https://qiita-image-store.s3...)`。実行例・出力の画面は画像で見せる。下書きでは `![説明](TODO:01_readme.png)` のように差し込むファイル名を書いておき、本人がQiitaの編集画面でアップロードしてURLを差し替える。
- **Mermaid・数式**：QiitaはMermaid（` ```mermaid `）と数式（` ```math `・`$...$`）を描画できる。ER図・フロー図はキャプチャではなくコードで載せてよい。
- **相互リンク**：内容が本当に対応している自分の記事・参考にした記事にだけリンクする。参考にした記事は文中か脚注でクレジットする。
- **目次/参考**：長編は手動の `## 目次 <!-- omit in toc -->`。参考サイトは、本文で未リンクの資料がある場合だけ。

## タイトルの付け方

内容がひと目で分かる語尾を選ぶ。著者の実績パターン：

- 学習ノート →「〜を勉強したのでまとめてみた」「〜まとめてみた」
- 自作物 →「〜を作ってみた」「〜してみた」
- 解説 →「〜を分かりやすく解説」「〜の違い」「〜活用術」
- 対処 →「〜の対処法」「〜する方法」（DB2/IE限定 など環境を `【】` で前置きすることがある）
- 体験 →「〜勉強法」「〜した話」「〜を振り返る」「〜感想」

盛りすぎ・煽りすぎない。

## 公開までの操作（qiita-cli）

このリポジトリは [qiita-cli](https://github.com/increments/qiita-cli) 管理。頼まれたら：

1. 記事ファイルを作る：`npx qiita new <basename>` → `public/<basename>.md` が生成される（フロントマターの雛形付き）。
2. フロントマターを埋める：
   ```yaml
   title: （タイトル）
   tags:
     - Java          # 技術名
     - PostgreSQL    # 技術名
     - 個人開発      # 層タグ（初心者 / 新人プログラマ応援 / 個人開発 / ポエム など）
   private: false
   organization_url_name: null   # works-hi に紐づけるかは毎回本人に確認する
   ```
   タグは**2〜5個**。「技術名＋概念＋対象読者の層」で構成。
3. 本文を書く（STEP 4〜7）。
4. プレビュー：`npx qiita preview`（Qiitaの認証情報が必要。無い環境では本人に確認してもらう）。
5. 公開／更新：`npx qiita publish <basename>`。

**注意**：`publish` は外部（Qiita）への公開・更新なので、ユーザーの明示的な指示なしに実行しない。原稿作成・ファイル化までにとどめ、公開はユーザーに委ねる。
本人が記事ファイルを直接編集・pushすることがあるため、追記の前に必ず最新を取り込み、本人の変更（フロントマター・画像URL・表記の修正）を消さない。
