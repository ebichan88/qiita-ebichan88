# templates.md — 記事タイプ別の骨格

各タイプの見出し構成・長さの目安・記法の使いどころ。実在記事の構成から抽出。
**骨格はあくまで型**。埋めるときは必ず [`voice.md`](voice.md) の語り口で肉付けし、SKILL.md の「AIっぽさ除去チェックリスト」を通す。

見出しレベルの原則：`##` を主セクション、`###`/`####` を小節に。冒頭 `## はじめに`。

---

## 冒頭に置く型：想定読者・前提・スコープ（全タイプ共通）

`## はじめに` の直後に、**読者と前提を早めに固定する**のが本人の型。まとめ・検証・解説系ほど厚く置き、Tips・ポエムは軽く（または省略）。生成時はこの3点を冒頭に置けるか必ず確認する。**特に解説・まとめ・検証で欠けていると「本人が書いた記事」に見えない。**

**① 想定読者（解説・まとめ・検証系で頻出）**
- 「誰に向けた記事か」と「前提知識」を明示する。`## 想定読者`（または `### 想定読者`）。
- 例：Reactor記事「Spring WebFluxでReactorを利用しており、基本を理解したい方」＋前提知識（ラムダ式・Stream APIの理解など）を箇条書き。TypeScript記事「Javaエンジニア／JSは触ったがTSは初めて」。

**② 前提（バージョン・環境）**
- 挙動・検証の話は必ずバージョンを出す。`## 前提` に `:::note info` かバージョン表で示す。
- 例：TypeScript 5.9.3 / Java 25（note）、Oracle 19c / PostgreSQL 12.12（表）、Reactor記事は Java / Gradle / Reactor Core のバージョン表。
- サンプルコードを公開しているなら `## 本記事で公開しているサンプルコードについて`（または `### サンプルコード`）でGitHubリポジトリを示す。

**③ スコープの明示（扱う／扱わない）**
- 「今回はここまで」「〜は割愛」「私が経験した範囲を取り上げる」と、**範囲を正直に区切る**。読者の期待とのズレを防ぐ布石であり、本人の謙虚さの表れでもある。
- 例：「Spring WebFluxそのものは今回扱いません」「非同期処理の `.catch()` は割愛します」「あくまで私自身が経験したマイグレーション部分を取り上げます」。
- 冒頭の `:::note warn` でサンプルコードの前提・約束事を宣言することもある（例：「OracleとPostgreSQLで比較します」）。

## 1. まとめてみた（学習ノート・長編）

ある技術をイチから勉強した記録。**最長クラス（3000〜1万字超）**。網羅的・リファレンス的。
代表：PL/pgSQL、Struts1.3.10、Project Reactor、DB2→PostgreSQLマイグレーション。

```
## はじめに                      ← 何を勉強し、なぜまとめるか。対象や動機
## （バージョン/前提について）    ← 検証環境・対象バージョンの明記
## 本記事で公開しているサンプルコードについて  ← リポジトリがあればリンク
## 目次                          ← 手動の目次（長編は必須）
## 事前準備（テストデータ投入 など）
## 〈大テーマ1〉                  ← 説明的見出し
### 〈項目〉について
### 〈項目〉について
## 〈大テーマ2〉
### …
## 参考サイト / 参考文献          ← 末尾に必ず
```
- 各小節は「概念の説明 → `sql:サンプル`/`java:サンプル` → 実行結果 → ハマりどころ」の順。
- 見出しは「〜について」で揃えることが多い（説明的モード）。
- OracleとPostgreSQL等、**2環境の対比は表とラベル付きコード**（` ```sql:Oracle ` / ` ```sql:PostgreSQL `）。
- 細かい注意は `:::note warn` と脚注へ。
- 「全部は書ききれないので詳細は公式/書籍を」と正直に範囲を区切る。

## 2. 解説（概念・違い・パターンを例示で教える）

特定の概念・言語機能・設計パターン・技術の違いを、**例示と対比で「分からせる」こと**に焦点を当てた記事。**中〜長編（2,000〜8,000字）**。
「まとめてみた」が"自分の学習ログ（網羅的リファレンス）"なのに対し、解説は**1テーマを深掘りして読者に理解させる**のが主眼。動機も「勉強したので」より「**実務で必要になった／触れて戸惑った**」が多い。
代表：関数型インターフェース活用術、JavaエンジニアがTypeScriptで感じた違い7つ、Template Methodパターン。

骨格は2つの形がある。

**A. 1テーマ深掘り型（段階的に良くする／Before→After）**
```
## はじめに            ← なぜ書くか（実務で必要になった等）／何を解説するか宣言
## 想定読者 / 前提      ← 上記「冒頭に置く型」。バージョン・前提知識
## 〈概念〉とは         ← 定義。参考記事を裸URLで添える
## 実装例 / 今回のコード ← 実コード（自分の過去記事・repoが理想）
###   Step0〜N、または 修正前 → 改善点 → 改善方針 → 修正後  ← だんだん良くする
## （アンチパターン / 注意点 / 使い所）
## まとめ / おわりに
```

**B. N個のポイント列挙型**
```
## はじめに
## 想定読者 / 前提
## 1. 〈観点1〉         ← 各観点で「概念 → 対比コード → 所感」
## 2. 〈観点2〉
## …
## おわりに            ← 全体所感、（長ければ参考文献）
```

- 見出しは**説明的モード（名詞句）**。物語見出しは使わない。
- 教え方の核は**対比**：Java vs TypeScript、Before vs After、想定 vs 実際 を**ラベル付きコードで並べる**。
- 抽象概念は**身近なアナロジー／親しみやすい例示データ**でかみ砕く（Excel・サイゼリヤ、マリオ・Alice/Bob など）。
- 段階的に良くする型では、各ステップで「**何が嬉しくて、まだ何が問題か**」を地の文で必ず挟む（箇条書きだけにしない）。
- 定義や主張には**出典**を添える（参考記事は裸URL、公式ドキュメントは `>` 引用＋リンク＋脚注）。
- 題材は**実体験・実コード**に接地させる（架空シナリオだけで完結させない）。
- 目次・参考文献は任意（長編なら付ける）。

## 3. 作ってみた（自作ツール紹介）

スクリプト・アドイン・ツールの紹介。**中編（1000〜3000字）**。
代表：ExcelアドインでINSERT文生成、Markdownテーブル定義書生成、WinMerge出力自動化。

```
## はじめに        ← どんな場面で困り、何を作ったか（実務の動機）
## 概要            ← 箇条書きで機能・対応範囲・前提
## 使い方          ← 呼び出し方・引数・記法
## 実行例          ← 画像 or 入力例
## 実行結果        ← 画像 or 出力。表で仕様を補足
## ソースコード     ← 全文を ```lang:ファイル名 で。冒頭にコメントで概要/使い方/引数
## （設定方法/導入手順） ← 必要なら。外部の詳しい記事に委ねることも
```
- 「概要」は体言止めの箇条書きでOK（機能一覧）。
- ソースは省略せず全文を載せがち。コメントヘッダ（`[概要][使い方][引数]`）を付ける。
- 「実行結果を見てもわかる通り、〜できていることを確認できました」と結果を地の文で確認する。

## 4. Tips・対処法（短編）

詰まった事象と解決。**短い（600〜1500字）**。`## おわりに` は無くてよく、解決策で締める。
代表：DB2の文字列連結でNULLが出る、Firebaseコマンドが動かない。

```
## はじめに        ← 事象の前提を短く。関連する自分の記事へリンク
## 〈再現〉        ← 期待する結果と、実際の結果（```text:期待/実際 で対比）
## 原因            ← なぜ起きたか。表やコメントで指し示す
## 解決策          ← **結論を太字で一行**、直し方のコード（```lang:修正例）
```
- 「ところが・・・」「このままだと〜されません」と、詰まりを実況する語りが効く。
- 解決策の核は太字一文（例：**NULLを空文字に変換しましょう。**）。
- 前提知識は別記事に飛ばす（「そもそも〜って方は[こちらの記事](URL)をご覧ください」）。

## 5. 検証（挙動の確かめ）

仕様差や挙動を、仮説→実験→結論で検証。**中〜長編**。脚注多め。
代表：PL/SQL と PL/pgSQL のトランザクション制御の違い。

```
## はじめに        ← 何を検証するか、なぜ気になったか（移行で困った等）
## 前提 / 検証環境  ← バージョン・条件
## 〈観点1〉        ← 「〜はどうなるか？」を立て、コードで実験
### 検証            ← ```sql:パターン1 … 実行結果
### 結果 / 考察     ← 何が分かったか
## 〈観点2〉…
## まとめ / おわりに ← 表で結論を一覧化、移行時の注意
```
- 「単純に構文を変更する対応ではなく、既存ロジックの修正が要る」といった**実務インパクト**に触れる。
- 「これが正解とは限りませんが」と留保しつつ結論を出す。
- 比較結論は表でまとめる。

## 6. 勉強法・合格体験記

資格取得の記録。**中編**。淡々と再現性重視だが、焦り等の感情も入れる。
代表：Java Silver / Gold、基本情報技術者。

```
## はじめに        ← いつ・何に合格したか、書き残す動機
## 勉強期間        ← 開始/受験日、総勉強時間
## 自身のスキル     ← 受験時点の前提（実務経験の有無など正直に）
## 使用参考書       ← 書名リンク＋一言（「いわゆる黒本」等）
## 合格の秘訣       ← 結論を太字で（**ひたすら黒本を解きまくる**）
### 勉強時間        ← いつ・どれだけ
### 自身の勉強法     ← #### で時系列ステップ（1周目/2周目…）
## 結果            ← 得点率と合格ライン
## （関連資格の体験記はこちら） ← 自分の記事へ相互リンク
```
- 得点推移は表（周回×章）。
- 「正直これだけで合格できます」など体験に基づく本音の断言をひとつ。
- 「1周目は散々でした」「かなり焦りました」と感情も残す。

## 7. 読書感想（技術書）

技術書を読んだ感想。**中編**。引用と自分の現場経験の接続が核。
代表：良いコード/悪いコードで学ぶ設計入門。

```
## はじめに            ← いつ読んだ、勉強になった、備忘録も兼ねて
## この本を知ったきっかけ
## 全体の感想          ← これまでの学習遍歴 → 本書で得た軸（キーワードを太字）
## 特に気になった章の感想 ← 「詳細には触れないので気になる方は購入を」と断る
### 第◯章 〈テーマ〉    ← 定義を `>` で引用＋脚注で出典、自分の現場経験と接続
## おわりに            ← 未熟さの自認、繰り返し読む/手を動かす宣言
```
- 定義は `> 引用` ＋ 脚注 `[^n]` で出典（書名・ページ）を明記。
- 「現場で〜という実装を見た／こういう経験をした」と必ず自分の経験に接続する。
- ネタバレしすぎず「気になった方は本書を」と誘導。

## 8. ポエム・振り返り（体験談）

転職・開発プロセス・DXなどの経験談。**中〜長編**。ここは**物語見出し（voice.md参照）**が主役。
代表：転職1年の振り返り、Claude Codeで個人開発1ヶ月、GAS×GoogleFormで囲碁大会DX。

```
## はじめに            ← 状況設定。「気づけば〜が経ちました」等
## 〈背景〉            ← 前職/現職、開発対象など前提を箇条書きで整理
## 1. 〈状況が動く一文〉  ← 物語見出し：困り→対処→次の困り、を時系列で
## 2. 〈次に起きたこと〉
## 3. …
## 〈図解〉            ← 全体像は mermaid の flowchart 等でまとめることも
## おわりに            ← 得た気付き、読者への配慮、次への意欲
```
- 見出しは一人称・時系列・感情/状況変化の一文（例：「AIレビューを入れたら、今度は自分が転記係になった」）。
- 「はじめからこの形だったわけではなく、困るたびに継ぎ足した結果」という**等身大の過程**を強調。
- 対比（前職/現職、理想/現実）を素直な濃淡で。左右対称に整えすぎない。
- 補足・留保・「あくまで一例」は脚注へ大量に逃がす。
- プロセス系は `## おわりに` で一段引いた展望（「〜の重要性が高まるのではと感じました」）。

## 長さと密度の目安（実測ベース）

| タイプ | 目安 | コード密度 | note/脚注 | 目次/参考 |
| --- | --- | --- | --- | --- |
| まとめてみた | 3,000〜10,000字+ | 非常に高い | 多い | あり |
| 解説 | 2,000〜8,000字 | 高い | ときどき | 任意（長編は付ける） |
| 検証 | 2,000〜5,000字 | 高い | 多い | ときどき |
| 作ってみた | 1,000〜3,000字 | 高い（全文掲載） | 少なめ | まれ |
| 読書感想 | 1,500〜3,000字 | 低い（引用中心） | 脚注で出典 | なし |
| 勉強法 | 1,500〜2,500字 | ほぼ無し | 少なめ | 相互リンク |
| ポエム・振り返り | 2,000〜6,000字 | 低い | 脚注が主役 | なし |
| Tips・対処法 | 600〜1,500字 | 中（断片） | 少なめ | 相互リンク |

字数はあくまで幅。**内容が短くて済むなら短く**するのも本人の流儀（Tipsを無理に膨らませない）。
