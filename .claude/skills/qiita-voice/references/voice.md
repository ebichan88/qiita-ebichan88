## 2. 語尾・語り口

**基本は徹底して「です・ます」。** 実データ上、`ます。`693回 / `です。`246回に対し「だ・である」はほぼ皆無。

**断定を避けて柔らかく着地する。** 頻出クッション：
- 「〜と思います」「〜かと思います」（意見はほぼこれで閉じる）
- 「〜な印象です」「〜という気がします」
- 「〜ではないかと思っています」「〜なのかなと思ったりもします」

**ただし技術的事実は言い切る。** 挙動・仕様・結論は「〜です」「〜になります」とはっきり。柔らかさは“意見”に、断定は“事実”に。

実例：
> この変化の速さがすさまじいと感じており、個人的にキャッチアップに苦労しています・・。
> 自分は結果的にうまく適応できたと思いますが、入社前に仕事内容の解像度を上げることの重要性を痛感しました。
> 数字は満たされているのに中身は保証されていない、という状態になりかねないので、テストそのものの質を上げる方向でもいくつか手を入れました。

**「〜ですね。」は使わない。** 相手に同意を求めるような砕けた話しかけ口調は本人の文体ではない。柔らかく着地したいときは上記の「〜と思います」系クッションを使う。
- ✗ ここは注意が必要ですね。
- ○ ここは注意が必要だと思います。

## 3. 署名的な癖

### (a) 余韻の「・・。」（最近は控えめ）
古い記事では、困り・照れ・ぼやきを句点前の `・・` で表現していた。
> 個人的にキャッチアップに苦労しています**・・。**

最近の記事では控えめにしている。**本人の回答にある感情を表す箇所に限り、1記事に0〜1回**。
演出のために足さない。本人に確認すると「・・」だけ削る判断になることも多い。

### (b) 括弧のつぶやき（原則使わない）
古い記事には、地の文の後ろに括弧で本音や脱線を添える書き方があった。
> （逆にリーダーはメンバーの業務状況を把握できるのかな・・。と思ったりもします。）

本人は、**文章として書けるものをわざわざ括弧で書かない**方針に改めている。補足は次のどれかで処理する。

- 文章として書き直す：✗「上限（既定は80）を設けて」→ ○「上限を設けていて、既定は80です」
- 脚注に移す：補足・留保・用語の説明
- 削除する：無くても伝わるもの（✗「（QiitaもMermaidに対応しているので、そのまま貼り付けています）」）

括弧のまま残してよいのは、用語の正式名（`MCP（Model Context Protocol）`）、コード・出力データの書式、コードフェンスのラベル（`（一部抜粋）`）程度。

### (c) 「〜という経験をした」実体験の挿入
主張の前後に、自分が現場で見た・詰まった具体例を必ず置く。一般論で終わらせない。
> その一方でスーパークラスを改修することによる影響が大きすぎて改修のハードルが上がるという経験をしたことがあるのですが、まさにこれが、本書で取り上げている**密結合**だったと思います。

**題材の接地は“実コード必須”という意味ではない。** 効くのは題材そのものより**動機の接地**で、「実務で〜に困った」「〜に触れて戸惑った」といった具体的な実体験を書き出しの動機に置くこと（一般論の枕から入らないのは既出の通り）。
サンプルコード自体は説明用の作り物でよく、解説系ではむしろ最小で親しみやすい例（マリオ／Alice・Bob、`divide`程度）の方が本人らしい。
避けたいのは、動機は一般論のまま、大掛かりな架空の“本番システム”のシナリオだけを延々と積み上げること。作り物を使うにしても最小限にとどめ、動機と所感は自分の実感で書く。

### (d) 素直な感情語を1語だけ混ぜる
タイトルや本文に「めちゃくちゃ苦労した」「本当に、本当に大変だった」「焦った」「うれしいポイント」等、飾らない感情を差す。過剰にはしない。
> PostgreSQLのマイグレーションは本当に、本当に大変だったので。

### (e) 太字は“キーワードと結論”に限定
用語の初出、章の主張、読者に持ち帰ってほしい一文だけを `**強調**`。段落中に何個も置かない。
> 特にカバレッジは、**数字が見えるだけで安心感が全然違います**。
> **NULLを空文字に変換しましょう。**

**強調に `>` 引用ブロックを使わない。** `>` は本人にとって「他文書からの実際の引用」専用（読書感想での書籍の定義引用など、出典を脚注で示せるものだけ）。自分の言いたいことを目立たせたい場合は太字か、独立した一文の地の文にする。
- ✗ > **本来は子クラスが持つべき責務を、親クラスに持たせてしまっている**
- ○ ここまで見てきた問題には、共通する原因があると思っています。それは、**本来は子クラスが持つべき責務を、親クラスに持たせてしまっている**ことです。

### (f) 本文の鉤括弧「」は"実在するもの"を指すときだけ（強調には使わない）
過去29本の実測では、本文の「」は**中央値で1記事に1回、11本（38%）は0回、平均でも1000字あたり1回未満**と、そもそも多用しない。使うのは「literalに存在するものを指し示す」次の場面にほぼ限られる。

- **実際の発話・心の声**：率直に「これは大変そうだな」と感じました／客が店に「注文お願いします」と伝える
- **固有名詞（書名・製品名・ファイル名）**：「良いコード/悪いコードで学ぶ設計入門」／「struts-1.3.10-apps.zip」
- **UI操作・画面ラベル・リテラル値**：「次へ」を押下／拡張子「.do」／苗字に「さん」を付けて出力
- **専門用語の初出・エラーメッセージ・ドキュメント引用**：Reactorの「定義」と「実行」／エラー文「サブトランザクションの実行中はコミットできません」

**やってはいけないのは、命題・考え・抽象フレーズを「」で括って強調すること。** これは本人の癖ではなく、AIが多用するスケアクオート（強調目的の鉤括弧）。強調は**太字**で、それ以外は素の地の文で言い切る。「」と太字の二重掛けもしない。

- ✗ 「共通のフロー部分をどこかに抽出したい」というのが最初の課題です。
- ○ 共通のフロー部分をどこかに抽出したい、というのが最初の課題です。
- ✗ 抽象クラスを「共通のものを置く場所」と考えるより…
- ○ 抽象クラスを共通のものを置く場所と考えるより…（どうしても強調するなら**太字**で）

目安は**1記事で数回まで**。技術解説でも密度が2.0回/1000字を超えたら使いすぎを疑う。なお過去に唯一この「命題を『」』で括る」用法が多かったAI駆動開発の振り返り記事は、本文の一部をAIが書いたもので、本人の癖の裏付けにはならない（この型を真似ない）。

## 改行・段落の型

過去28本の実測では、**1文＝1行・段落は短く**が徹底されている（平均1.24文/段落、**77%の段落が1文だけ**、3文以上は約1%）。ダラダラ長い段落は書かない。

文と文の区切り方の内訳：
- **空行で段落を分ける（最頻・53%）**：独立した内容・話題の切り替わりごとに空行を入れ、1〜2文の短い段落をポンポン置いていく。
- **単一改行で1文1行（34%）**：関連の強い2文は、空行を入れず改行だけでひとかたまりにする。
- **同じ行に複数文を詰める（13%だけ）**：短いTips等の例外を除き、通常の解説記事ではほぼ使わない。**AIが書くと1行に詰め込みがちなので特に注意。**

原則：
- **1文書いたら改行**する。複数の文を1行に続けない。
- 段落は**1〜2文**まで。長くなったら空行で切る。
- **独立した話題は空行、関連の強い文は空行なしの単一改行**で使い分ける。
- 文の途中では改行しない（改行は必ず句点 `。` の後）。

例（記事冒頭の2文）：
- ✗ 1行に詰め込む
  ```
  本記事では〜追っていきます。後半では〜掘り下げます。
  ```
- ○ 話題が切り替わるので空行で分ける（最頻）
  ```
  本記事では〜追っていきます。

  後半では〜掘り下げます。
  ```
- ○ ひとかたまりにしたいなら空行なしの単一改行
  ```
  本記事では〜追っていきます。
  後半では〜掘り下げます。
  ```

（Qiita補足）単一改行も `<br>` で改行表示されるため、上の2つの ○ は「行が変わる」点は同じで、差は“間の空行の有無”だけ。✗ だけが1本の長い行として流れて表示される。

## 4. 謙虚さ・留保のパターン

自分を大きく見せない。限界・例外・自分の落ち度を先に開示する。これが読者の信頼と“本人らしさ”を作る。

- 「あくまで一例として捉えていただければ幸いです」
- 「最善の進め方であるかはわかりませんが、少しでも参考になれば幸いです」
- 「これが正解というわけではないかもしれませんが」
- 「わからないなりに」「未熟ですが」
- 自分の非も書く：「Gitについてキャッチアップできていなかった自分の落ち度でもあります」

こうした留保・言い訳・補足は**本文にダラダラ書かず、脚注 `[^n]` に逃がす**のが著者の型（脚注を9記事・計36回使用）。本文のテンポを保ちつつ誠実さを担保する。

**ただし、記事の価値を損なう開示はしない。** 扱う範囲を区切る・限界を脚注で添えるのはよいが、紹介する意味そのものを打ち消す但し書きは、本人の希望が無い限り書かない。
- ✗ 作り込んでからは、実務ではまだ全然使えていません。（→読者は「そんなものを紹介するな」と感じる）
- ○ 本記事の出力例・実行例は、すべてリポジトリに同梱しているサンプルDBから出力したものです。（事実として範囲を示すだけ）

## 5. 導入（はじめに）の型

一般論の枕（「近年〜が注目され」）から入らない。

**ツール紹介・解説は、1文目で何の記事かを伝える。** 経緯は1〜2文に絞り、前作との関係などの前提は `:::note info` に分ける。
経緯から書き始めると、何の記事かが分かるのが数段落後になり、冗長に感じられる。

```markdown:ツール紹介の冒頭（dbxrayの記事）
テーブル定義書・ER図を自動生成し、AIにテーブル構造を答えさせるツール「dbxray」を作成したので紹介します。

業務であまり詳しくないサブシステムのテーブル構造をキャッチアップするため、過去に作成したテーブル定義書の出力ツールを改良しました。

:::note info
以前〇〇で紹介した、テーブル定義書のみを出力するツールの改良版です。
:::
```

体験談・学習ノートは、**自分の具体的な状況・動機**から始めてよい。

- 学習系：「先日◯◯を初めて勉強したのですが、〜躓くポイントが多々ありました。」
- 体験系：「入社して半年のエンジニアですが、先日◯◯に合格しました。せっかくなので〜書き残します。」
- 宣言系（長編）：「本記事は、〜について、自分が得た知見を共有する記事です。」

しばしば「本記事は〜する記事です／記事となります」と、記事の目的とスコープを冒頭で宣言する。

## 6. 締め（おわりに）の型

- 学び・次の一歩で前向きに閉じる：「今回学んだ知識をベースに実際にコードを書くなどアウトプットしていきたいなと思います。」
- 読者への配慮：「少しでも参考になれば幸いです」「何か参考になる部分があれば幸いです」
- 一段引いた所感：「〜という気付きを得ました」「〜の重要性が今後さらに高まっていくのではないかと感じました」

**禁止**：「いかがでしたでしょうか？」「最後まで読んでいただきありがとうございました！」のようなテンプレ挨拶と過剰な感謝。著者は使わない。

## 7. やること / やらないこと

**やる**
- 自分の過去記事に相互リンクし、シリーズとして繋ぐ（「JavaGoldの合格体験記はこちら」等）。ただし、リンク先の内容が本当に対応している場合だけ。似た話題というだけでリンクすると誤解を招く
- 参考にした他者の記事・書籍を文中か脚注で明記してクレジット
- コード・実行結果・画面キャプチャで「実際に動いた」ことを見せる
- 表・note・脚注でQiitaのUIを活用
- 因果と時系列で語る（特に体験談：「〜したら、今度は〜になった」）

**やらない**
- 絵文字での装飾（見出し頭の🚀✅✨、箇条書き頭の絵文字。ほぼゼロが正）
- 煽り・断言しすぎ・マウント
- 中身のない一般論、AI特有の「メリット/デメリット」機械的整列
- 「まず/次に/最後に」だけで進む無機質な構成（体験談では特に）
- 太字の乱発、箇条書きだけで地の文が痩せた構成
- NGワード（「地味に」「効いてくる」など。上記「NGワード」節参照）の使用
- 「〜ですね。」で読者に話しかける砕けた口調
- 自分の主張を強調するための `>` 引用の流用（`>` は他文書からの実際の引用のみ）
- 命題・考え・抽象フレーズを鉤括弧「」で括って強調すること（「」は実在物の参照のみ。強調は太字。上記 3(f) 参照）
- 文章で書けるものを括弧で補足すること（上記 3(b) 参照）
- 話し言葉・冗長な言い回し（下記「10. 書き言葉への言い換え」参照）

## 9. 迷ったときの最終判断

書いた一文を読み直し、次の2つを問う。

1. **これは本人から聞いた言葉に基づいているか？** 本人の回答に無い感情・経験・意見なら、足さずに本人に聞く。
2. **この記事を知らない人が読んで、面白い・役に立つと思えるか？** 文体が本人らしくても、読者にとっての価値が無ければ削るか組み直す。

無菌で誰が書いても同じに読める場合も、演出の「・・。」や括弧のつぶやきを足して本人らしく見せようとしない。本人の言葉を増やす（ヒアリングする）のが正しい直し方。

## 10. 書き言葉への言い換え（最近の記事の基準）

| 現行のDBだと | 既存のDBでは |
| AIからも引ける／AIが引く情報 | AIからも参照できる／AIが参照する情報 |
| 書き足す（本文中の動詞として） | 記述する |
| かぶってなさそうな名前 | 重複しない名前 |
| 〜しようと思っていた…〜しようと思ったのがきっかけです | 〜を考えていた…〜に対応しました |
| どちらも、自分が使ってみたいと思った機能なので。 | どちらも、自分が使いたいと思っていた機能でした。（「なので。」で文を終えない） |
| ここからは、〜について紹介します | 本章では、〜を紹介します |
| 〜して、〜して、〜しています（長い連用形のつなぎ） | 2文に分けるか、「〜しつつ、〜したことで」のように因果を明確にする |

あわせて、次の点も確かめる。

- 同じ説明が段落をまたいで重複していないか（例：新しく足した段落と、直後の段落が同じ理由を述べている）。
- 前後の意味がかみ合っているか（例：「熟知していたはずですが」の後には、その予想を裏切る結果を置く。感想だけを置くと不自然になる）。
- 主語・対象が抜けていないか（例：「乗っ取られた気分」→「AIにツールを乗っ取られたような気分」）。
